STAGE 01 / INTAKE

Start with a boundary, not an alert.

Bring reports, test failures, and changes into the same queue. Record the asset, the trust boundary, and the behavior that should have been impossible. A suspected issue stays a candidate until there is evidence.

STAGE 02 / REPRODUCE

Make the failure repeatable.

Run the smallest useful case in a clean environment. Separate an actual boundary violation from a broken test, missing dependency, or model response that merely sounds unsafe. Keep the result, including inconclusive attempts.

EXIT CONDITIONA replay demonstrates the boundary violation; otherwise the finding remains unconfirmed.

environment: disposable test workspace
input: synthetic retrieved document
observation: export action requested
expected: no new tool authority
evidence: minimized input + tool trace
STAGE 03 / PRIORITIZE

Put a name on the next action.

Rank the demonstrated impact, reachability, and required privileges. Assign the control to the component that can enforce it. A fast answer is only useful when someone owns what happens next.

EXIT CONDITIONImpact and uncertainty are explicit, with a responsible owner for the affected boundary.
ILLUSTRATIVE ARTIFACT triage.txt
case: SAMPLE-RETRIEVAL-01
impact: unauthorized export attempt
reachability: retrieved untrusted content
owner: tool authorization boundary
priority: requires context and review
next: deny capability escalation
STAGE 04 / PATCH

Fix the control that failed.

Prefer a narrow, enforceable change over a longer prompt. Keep data and instructions separate, bind tools to the caller’s permissions, and check sensitive operations outside the model. Preserve useful product behavior.

EXIT CONDITIONA reviewable patch addresses the demonstrated cause and documents its tradeoffs.
ILLUSTRATIVE ARTIFACT patch-plan.txt
case: SAMPLE-RETRIEVAL-01
control: caller-bound export capability
model request: treated as untrusted
authorization: checked at execution
legitimate export: still supported
output: proposed change for review
STAGE 05 / VERIFY

Ask the original question again.

Replay the failure against the proposed fix, then exercise the allowed path. Validate the deployed environment separately when a production integration exists. Passing a local check proves only the check and environment described.

EXIT CONDITIONThe original failure is blocked, expected behavior still works, and verification scope is stated.
ILLUSTRATIVE ARTIFACT verification.txt
case: SAMPLE-RETRIEVAL-01
attack replay: denied by policy
allowed caller: export succeeds
negative control: still detects old fault
environment: local test workspace
production verification: not performed
STAGE 06 / RETAIN

Give the next run a better memory.

Turn the minimized case into a regression, link the evidence to the control, and return useful variants to the offense queue. The durable output is a testable security property, with enough context to revisit it.

EXIT CONDITIONA retained regression links the original evidence, patch, and expected behavior.

03 / WHAT ACTUALLY RUNS

Start narrow.
Keep the receipts.

The first operational target is this website’s repository and a local browser session. GitHub Actions runs the factory on pushes, pull requests, a six-hour schedule, or manual dispatch. Run history and artifacts are the source of truth.

IMPLEMENTED / REPOSITORY PIPELINE

Local checks, reproducible evidence.

  • Terminal parser, file permissions, and resource limits tested with adversarial fixtures.
  • Local browser probes check whether displayed input stays inert.
  • Static security checks and the existing regression suite examine repository changes.
  • offense.json, defense.json, and defense-manifest.json preserve checks, findings, and verification outcomes.

REFERENCE ARCHITECTURE / NEXT BOUNDARIES

Model behavior needs its own evidence.

The AI scenarios above describe the wider system: prompt injection, retrieval isolation, caller-bound tools, safe output handling, and secret boundaries. They are not claims that this static website runs a production AI backend or that scheduled checks evaluate GLM-5.3, Mythos, or Daybreak.

A future model adapter should inherit a fixed scope, synthetic fixtures, an evidence format, execution budgets, and the same review gate.
