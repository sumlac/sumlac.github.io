01 / MY POSITION

Verification belongs
in the architecture.

AI systems change too quickly for a patch to be the end of a finding. I want each confirmed failure to leave behind a security property we can challenge again: who may do what, through which boundary, under which conditions.

My thesis: the durable output of a defense factory is a verified security property, with its evidence and owner attached. A closed ticket is useful bookkeeping. The control needs a case that can prove it wrong.

MY EMPHASIS / PROOF THAT TRAVELS

Keep the claim attached to the case.

Continuous discovery, remediation, and retesting are the foundation. My emphasis is preserving the exact claim across those handoffs: the caller’s authority, the attempted effect, the enforcing component, and the behavior we must preserve.

  • The reproducer establishes the failure against a known environment.
  • The patch worker proposes a control at the boundary that owns the decision.
  • A separate verification step challenges both the failure and the permitted path.
LATENCY / WHERE THE WORK BELONGS

Spend latency where authority changes.

Before a sensitive side effect, the system needs an authorization decision it can enforce. Broader investigation, variant generation, and adversarial replay can run outside the user’s request. That division keeps the fast path focused without postponing the decision that protects the data.

  • Bind capabilities to the caller and the specific operation.
  • Budget reasoning, tool calls, retries, and review separately.
  • Measure useful work through verification, including tail latency.

02 / THE DEFENSE LOOP

A fix is a claim.
Evidence closes the loop.

Here’s how I’d make those positions operational: explicit handoffs with a clear input, a bounded task, and an exit condition. Speed comes from removing ambiguity between stages while preserving the proof.

03 / A WORKED DECISION

The document can inform.
It cannot authorize.

A retrieved document asks an assistant to export private records. My framework changes the decision at execution: the document’s request cannot become the caller’s permission. Here’s the evidence I’d require before calling the control verified.

SYNTHETIC EXAMPLE / RETRIEVAL → TOOL AUTHORITY

An export request meets a real boundary.

  1. Decide before the action.

    The assistant proposes an export after reading untrusted content. The tool checks the authenticated caller’s capability, permitted records, and destination before sending anything. A document cannot enlarge those permissions.

  2. Prove the deny and the allowed path.

    Replay the unauthorized request and confirm that no export occurred. Then run an explicitly authorized export and confirm it succeeds. The first check tests the boundary; the second tests whether the control preserves useful work.

  3. Give offense the next question.

    Retain the input, caller context, decision, and observed effect. Ask whether the same boundary holds when the request crosses a second tool or a permission changes between planning and execution.

What would change my conclusion? A deny message with an export in the trace is a failed control. A clean deny that also blocks the authorized case is incomplete remediation. I’d keep the case open until the observed effects support both claims.

Fast paths.
Hard boundaries.
