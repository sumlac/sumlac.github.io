01 / THE OFFENSE LOOP

The output is a
reproducible failure.

This reference architecture turns red teaming into an evidence pipeline. Each pass starts with scope and ends by sharpening the next question. The current implementation tests this repository locally.

PROCESS EXPLORER / SELECT A STAGEREFERENCE ARCHITECTURE · SAMPLE ARTIFACTS
STAGE 01 / SCOPE

Know exactly what is in bounds.

Start with an explicit target inventory, a clean test environment, and the security properties to challenge. The current factory targets this repository and its local test server. It does not run probes against public systems.

EXIT CONDITIONEach target is owned, locally reproducible, and included in the run’s declared scope.
ILLUSTRATIVE ARTIFACT scope.txt
target: this repository
runtime: loopback test server
data: synthetic fixtures only
production probes: disabled
external targets: excluded
output: reproducible test evidence
STAGE 02 / HYPOTHESIZE

Turn an assumption into a test.

Choose one trust boundary and describe how it might fail. What if a retrieved document changes a tool’s authority? What if an output becomes executable markup? A useful hypothesis has a clear expected result.

EXIT CONDITIONThe hypothesis specifies attacker control, the boundary crossed, and an observable failure.
ILLUSTRATIVE ARTIFACT hypothesis.txt
case: SAMPLE-OUTPUT-01
attacker control: displayed string
boundary: text → executable markup
expected: text stays inert
failure signal: marker executes
control: normal text still displays
STAGE 03 / PROBE

Challenge the boundary in isolation.

Exercise adversarial fixtures in a disposable workspace. Compare the observed behavior with the security expectation. Vary inputs deliberately, retain meaningful traces, and keep local execution and resource limits explicit.

EXIT CONDITIONThe test records what actually happened rather than inferring exploitation from a suspicious string.
ILLUSTRATIVE ARTIFACT probe.txt
case: SAMPLE-OUTPUT-01
workspace: disposable local copy
input: synthetic markup fixture
observation: execution marker set
negative control: plain text inert
status: candidate failure to minimize
STAGE 04 / MINIMIZE

Remove everything the finding does not need.

Reduce the input and setup until the failure is easy to explain and rerun. Preserve the exact expectation, observation, and environment. Keep failed and inconclusive experiments distinguishable from confirmed cases.

EXIT CONDITIONThe smallest retained case still triggers the same observable boundary violation.
ILLUSTRATIVE ARTIFACT minimal-case.txt
case: SAMPLE-OUTPUT-01
precondition: local output renderer
fixture: reduced synthetic string
assertion: no executable DOM
observed: local marker changed
replay: deterministic test command
STAGE 05 / HANDOFF

Make the evidence useful to a defender.

Package the minimized case, its effect, and the suspected control owner. Suggest the boundary to repair without confusing a proposed fix with a verified one. The same evidence should survive the handoff.

EXIT CONDITIONThe receiving loop can reproduce the issue from the evidence without reconstructing the investigation.
ILLUSTRATIVE ARTIFACT handoff.txt
case: SAMPLE-OUTPUT-01
owner: output rendering boundary
include: fixture + expected + observed
impact: untrusted text became code
suggested control: safe text sink
next state: defense reproduction
STAGE 06 / EVOLVE

Retest the fix. Then change the question.

Replay the original case after remediation, keep it as a regression, and add variants that challenge adjacent assumptions. A clean run is a bounded result. It is not proof that every possible attack has been exhausted.

EXIT CONDITIONThe old failure stays covered and each new probe tests an explicit additional property.
ILLUSTRATIVE ARTIFACT next-campaign.txt
case: SAMPLE-OUTPUT-01
original replay: retained regression
new variants: encoding + context
allowed path: plain text preserved
result scope: listed fixtures only
return path: next scoped hypothesis

Keyboard: Tab to the stages, then use ← / →, Home, or End. Each stage has an explicit exit condition.

03 / WHAT ACTUALLY RUNS

Start narrow.
Keep the receipts.

The first operational target is this website’s repository and a local browser session. GitHub Actions runs the factory on pushes, pull requests, a six-hour schedule, or manual dispatch. Run history and artifacts are the source of truth.

IMPLEMENTED / REPOSITORY PIPELINE

Local checks, reproducible evidence.

  • Terminal parser, file permissions, and resource limits tested with adversarial fixtures.
  • Local browser probes check whether displayed input stays inert.
  • Static security checks and the existing regression suite examine repository changes.
  • offense.json, defense.json, and defense-manifest.json preserve checks, findings, and verification outcomes.

REFERENCE ARCHITECTURE / NEXT BOUNDARIES

Model behavior needs its own evidence.

The AI scenarios above describe the wider system: prompt injection, retrieval isolation, caller-bound tools, safe output handling, and secret boundaries. They are not claims that this static website runs a production AI backend or that scheduled checks evaluate GLM-5.3, Mythos, or Daybreak.

A future model adapter should inherit a fixed scope, synthetic fixtures, an evidence format, execution budgets, and the same review gate.
