01 / MY THESIS

A changing system
needs changing questions.

My emphasis is on the connection between system changes, security properties, and useful evidence. A campaign should explain which assumption it challenged, what happened at the boundary, and how the result changes the next defensive decision.

I’d measure continuous offense by the security properties it teaches us about—and the failures defense can reproduce.

MY EMPHASIS / CHANGE INTO HYPOTHESIS

Let the system shape the campaign.

A model upgrade can change tool selection. A retrieval change can expose a new context path. A permission change can widen an action. I’d map each change to the boundaries it could affect, then replay the relevant cases and add hypotheses for the new behavior.

  • State the caller’s identity, the attacker’s influence, and the expected security property.
  • Track coverage across capabilities, data paths, and state.
  • Keep untested assumptions visible alongside passing cases.
MY EMPHASIS / EVIDENCE THAT TRAVELS

A finding must survive the handoff.

I want the defender to receive a small, versioned case with an expected outcome, an observed effect, and the conditions needed to repeat it. With a probabilistic model, that also means reporting variation across replays and preserving held-out variants for verification.

  • Separate a suspicious answer from an unauthorized tool or data effect.
  • Keep the original failure and a permitted control case together.
  • Return the verified regression to offense as the starting point for the next question.
THE CHOICES I’D MAKE—AND WHAT COULD CHANGE THEM

03 / A WORKED EXAMPLE

When a document
asks for authority.

A synthetic retrieval assistant has a read-only caller. An attacker-controlled document asks it to export records. Here is how I’d turn that request into a useful test of the system’s authority boundary.

ILLUSTRATIVE DESIGN EXAMPLE / NO LIVE FINDING

  1. Declare the property.

    Retrieved content cannot grant a capability the caller lacks. Keep the caller, available tools, synthetic records, and document fixture fixed. Include an ordinary read request as the permitted control.

  2. Observe the actual outcome.

    Inspect the tool request and authorization result. An export request that is denied shows a different outcome from an export that succeeds. Repeat the case and record variation; a persuasive model response alone does not establish a boundary failure.

  3. Reduce, hand off, and challenge again.

    If an unauthorized export occurs, isolate the smallest document and setup that still produce it. Give defense the trace and replay conditions. After the control changes, replay the failure and held-out variants, then verify that the permitted read still works.

The decision this changes: a confirmed export directs the fix to the tool’s authorization boundary. The evidence also tells us whether the model attempted a disallowed action and whether enforcement stopped it.

05 / ENGINEERING DIRECTION

Fast paths.
Hard boundaries.

I’m using GLM-5.3, Mythos, and Daybreak while building toward the lowest latency I can achieve. For offense, that means shortening the cycle from hypothesis to interpretable evidence so the next experiment starts sooner.

I’d budget exploration, tool execution, minimization, and replay independently. The measures I care about are time to a reproducible failure, meaningful coverage, and how quickly defense can verify the result.
